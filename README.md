# Collaborative Inference with User Edge Devices

This repository contains the simulator and supporting data-processing code for *Collaborative Inference with User Edge Devices toward QoS-Aware Autoscaling*. The system combines a continuously available dedicated server with computing, storage, and network resources volunteered by online user devices. Requests are partitioned into subtasks that can be downloaded, executed, and uploaded on either the server or participating user devices. The aim is to absorb increasing demand with volunteered capacity while preserving useful quality-of-service (QoS) and limiting dedicated-resource growth.

The simulator is a discrete-time generative Markov model. At one-second steps it evolves user availability, inference requests, allocated resources, subtask readiness, subtask execution phases, and resource consumption. Statistical models fitted to measurements provide plausible dynamics for resource availability, resource consumption, and subtask completion. Scheduler and executor policies then make the placement and feasibility decisions whose effects are evaluated in simulation.

## Reproducibility workflow

There are two ways to use the repository:

1. **Run simulations from fitted models.** Use this path when the fitted JSON files in `resources/models` are available. It is the shortest route to reproducing simulation results.
2. **Rebuild the fitted models.** Collect new measurements, preprocess them, fit candidate models, select the lowest-AIC models, and then run simulations. This path is useful when reproducing the modeling pipeline on another machine or with new measurements.

The simulation experiments generated by this repository use 100, 1,000, 5,000, and 10,000 users, user-capacity multipliers of 1x and 2x, server-capacity multipliers of 10x, 30x, 50x, 80x, and 100x, and 100,000 one-second timesteps. These values are defined in [scripts/generate_simulation_experiments.py](scripts/generate_simulation_experiments.py).

## Requirements and installation

Use Python 3.13 and `pip`. A CUDA-capable GPU is optional; simulations can run on CPU, although the full experiment grid is computationally intensive.

```bash
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Run all commands from the repository root so that relative paths in experiment configurations resolve correctly.

## Configuration

The code reads an optional `config.json` from the repository root. Create it from [config_example.json](config_example.json):

```bash
cp config_example.json config.json
```

The configuration controls:

| Key | Default | Purpose |
| --- | --- | --- |
| `resource_dir` | `resources` | DNN weights, raw/processed data, and fitted statistical models |
| `temp_dir` | `tmp` | Measurement logs and saved simulation trajectories |
| `experiment_dir` | `experiments` | JSON experiment descriptions; omit this key to use `experiments` |

`config.json` is local configuration. The experiment classes load `experiments/exp_<handle>.json` when a script is invoked with `--experiment <handle>`.

## Run simulations from fitted models

### 1. Generate simulation experiments

The generator expects a directory containing the selected fitted models, including available-resource, resource-consumption, and task-completion models. The default model directory is `resources/models`:

```bash
python -m scripts.generate_simulation_experiments \
    --model_dir resources/models \
    --output_dir experiments
```

This creates experiment JSON files for CPU and CUDA execution. CUDA experiments require a working PyTorch CUDA installation; use a `cpu` experiment handle otherwise. The generated configurations use these scheduler policies:

| Paper terminology | Experiment configuration | Meaning |
| --- | --- | --- |
| Centralized scheduler | `centralized` | Executes subtasks only on the dedicated server |
| Uniform scheduler | `default` | Distributes eligible work across available nodes without affinity-based placement |
| Affinity-based scheduler | `smart` | Co-locates equal partitions where possible to increase batching |

Some generated `smartx` configurations use the same `smart` implementation with a server-priority scale. The executor policy is `default` in the supplied configurations and enforces node-level resource constraints by pausing or aborting infeasible work.

### 2. Run one experiment

Pass the handle without the `exp_` prefix or `.json` suffix. For example:

```bash
python -m scripts.run_simulation --experiment simulation_cpu_0
```

The simulator saves a trajectory under the configured temporary directory and prints the output path. The trajectory is used by the notebooks to calculate request completion, cancellation, latency, resource-consumption, and subtask-completion metrics.

To run the complete paper grid, iterate over the generated `exp_simulation_cpu_*.json` or `exp_simulation_cuda_*.json` files and pass each filename-derived handle to `scripts.run_simulation`. The full grid is large; start with one CPU experiment to verify the installation.

## Rebuild statistical models from measurements

Existing fitted JSON files can be reused by starting at [Generate simulation experiments](#1-generate-simulation-experiments). The steps below describe the longer modeling path.

### 1. Prepare DNN weights

The DNN weights are needed when collecting task download and execution measurements, because the measurement scripts run the model partitions. They are not needed to run simulations from already fitted JSON models. Download them before the task-measurement stage:

```bash
python -m scripts.setup_models
```

This stores weights under `resources/dnns` (or the configured `dnns` directory).

### 2. Collect measurements

Create the output directory configured by `temp_dir`, then collect available-resource traces. These collectors run until interrupted with `Ctrl-C`:

```bash
mkdir -p tmp
python -m scripts.measurements.measure_resources
python -m scripts.measurements.measure_bandwidth
```

Preprocess the raw traces with `scripts/available_resources/preprocess_available_resource_data.py`. Its output is the CSV consumed by the available-resource fitting experiments.

### 3. Fit available-resource models

Generate candidate ARIMA configurations for inbound/outbound bandwidth, CPU, memory, and storage:

```bash
python -m scripts.measurements.generate_fit_available_resource_model_experiments \
    --df_path <preprocessed-available-resources.csv> \
    --output_dir <available-model-candidates> \
    --exp_output_dir experiments
```

Fit each generated `exp_fit_avail_*.json` experiment:

```bash
python -m scripts.available_resources.fit_available_resource_model \
    --experiment <fit-available-handle>
```

Select the lowest-AIC candidate for each resource:

```bash
python -m scripts.save_best_models \
    --src_dir <available-model-candidates> \
    --output_dir resources/models
```

### 4. Measure task phases and fit their models

Use the fitted bandwidth models to generate download and execution measurement configurations, then run the collectors. The bandwidth limits and trial count are experiment choices:

```bash
python -m scripts.measurements.generate_download_experiment \
    --n_trials <trials> \
    --bandwidth_in_model_path resources/models/available_bandwidth_in_model.json \
    --output_path experiments/exp_<download-handle>.json \
    --max_bandwidths <bits-per-second> [<bits-per-second> ...]

python -m scripts.measurements.measure_task_downloads \
    --experiment <download-handle>

python -m scripts.measurements.generate_execution_experiment \
    --n_trials <trials> \
    --bandwidth_in_model_path resources/models/available_bandwidth_in_model.json \
    --bandwidth_out_model_path resources/models/available_bandwidth_out_model.json \
    --output_path experiments/exp_<execution-handle>.json \
    --max_bandwidths_in <bits-per-second> [<bits-per-second> ...] \
    --max_bandwidths_out <bits-per-second> [<bits-per-second> ...]

python -m scripts.measurements.measure_task_executions \
    --experiment <execution-handle> \
    --image_dir <directory-for-measurement-images>
```

Preprocess the download and execution traces and augment task-completion data:

```bash
python -m scripts.resource_consumption.preprocess_task_download_data \
    --data_path_pattern <download-data-pattern> \
    --output_path <download-data.csv>

python -m scripts.resource_consumption.preprocess_task_execution_data \
    --data_path_pattern <execution-data-pattern> \
    --output_dir <execution-data-dir> \
    --output_name_prefix <prefix>

python -m scripts.resource_consumption.augment_task_completion_data \
    --src_path <task-data.csv> \
    --output_path <augmented-task-data.csv>
```

Generate and fit resource-consumption candidates with `generate_fit_resource_consumption_model_experiments.py` and `fit_resource_consumption_model.py`. Generate and fit task-completion candidates with `generate_fit_task_completion_model_experiments.py` and `fit_task_completion_model.py`. Run each generated experiment using the same `--experiment` convention. Finally, run `save_best_models` with a source directory containing all candidate models and `resources/models` as the output directory. The selector chooses resource models by AIC and selects a compatible download/execution/upload task-completion model combination.

## Model and policy structure

The simulator advances a structured state at one-second intervals. The code’s state variables correspond to the paper’s availability, request, allocation, readiness, execution, consumption, duration, and action variables; the names are implementation-oriented and are not intended to reproduce the paper notation exactly.

The dedicated server is always available. User devices alternate between online and offline states, can submit at most one active request, and may volunteer resources while online. The executor policy enforces allocated CPU, memory, storage, and bandwidth limits; this is why scheduled work may be paused, aborted, or later resumed.

Key implementation surfaces are [simulation/model.py](simulation/model.py), [simulation/simulation.py](simulation/simulation.py), [simulation/transition_functions.py](simulation/transition_functions.py), [simulation/policies.py](simulation/policies.py), [models/experiments.py](models/experiments.py), and [utils](utils).

## Tests and analysis

Run the unit tests after installing the dependencies:

```bash
pytest
```

The tests focus on transition functions and scheduler/executor policies. The notebooks in [notebooks](notebooks) analyze fitted models and trajectories, including resource availability, task completion, request latency, and simulation behavior. They expect the relevant raw data, fitted models, and trajectory outputs to exist under the configured directories.
